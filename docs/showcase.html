§ 01 — The brief

A single operator with analyst-grade reach.

The brief was deceptively simple. A junior analyst spends most of a research session juggling tabs — a price tracker for the equity, a CRM for the customer book, a vector store for internal notes, a workspace for draft briefs, an inbox for the eventual report. An agent that orchestrates all of that — fetching real numbers, citing real customers, writing real files, sending real email — would compress hours into minutes. But only if the human stays in control of every action that touches the outside world.

What shipped is a multi-step LangGraph state machine running on Amazon Bedrock AgentCore Runtime, exposing thirteen tools across five domains, with every side-effect routed through an explicit interrupt-and-approve checkpoint. Read-only research happens immediately; anything that changes the world pauses and asks. Both halves are durable across containers and across sessions.

§ 02 — What the agent does

Thirteen tools, five domains, one operator.

Eight read-only tools execute on demand. Three side-effect tools pause the graph and surface a human-approval request. Two more — browser and voice — are designed and queued for the next wave. Every tool name, schema, and behaviour is reviewed at the agent boundary; nothing reaches the world without explicit consent.

§ 03 — Architecture

Six stacks, one graph, zero servers.

The entire deployment is defined in AWS CDK — six stacks composing storage, secrets, MCP-as-Lambda tools, a Cognito-gated Gateway, the AgentCore Runtime hosting the agent container, and an observability layer. The agent itself is a LangGraph state machine: retrieval first, then research, then generation, with an approval node sitting in front of every side-effect tool.

AgentCore Runtime Serverless container hosting LangGraph. Same image runs locally; same /invocations contract.
02
Gateway + 3 Lambdas MCP-over-HTTPS abstraction over yfinance, SQLite CRM and S3 workspace. Cognito-authenticated.
03
AgentCore Memory Durable checkpoint store. Containers become stateless — HITL approve survives any router decision.
04
Amazon SES IAM-scoped send via boto3. Verified sender identity. Sandbox today, prod-access ready.
§ 04 — Engineering decisions

The hard parts, made hard on purpose.

Four pieces of work define the shape of this system. They were not on the original product spec — they emerged from production, from incidents, from a QA pass that refused to accept silence.

Decision · 01

An atomic approval gate, not a chat about it.

When the agent decides to call a side-effect tool — write a file, save a memory, send an email — the LangGraph node approval calls interrupt(). The graph pauses, the runtime returns status: "interrupted" with the pending operation in the response body. Nothing has happened yet.

The caller resumes with Command(resume="approve") or "reject". The decision is atomic across the whole batch — a single reject cancels every pending call in the turn, even read-only ones, because partial execution is the worst of both worlds.

The agent will not invent a way to act. It will tell you what it wants to do, in your own schema, and wait for you to type the word.

Decision · 02

A checkpoint store that follows the agent, not the container.

The first deploy used an in-memory checkpointer. Then the AWS Console Runtime Playground crashed every /approve with a 500. The console mints a new runtimeSessionId per "Run" click — different container per click, no shared RAM, no checkpoint.

We swapped InMemorySaver for AgentCoreMemorySaver — the AWS-maintained BaseCheckpointSaver backed by the AgentCore Memory service. Same construct that was already provisioned for episodic memory. Zero new infra. State keyed by (actor_id, thread_id) reads from any container in the fleet.

The container is now stateless with respect to the conversation. The conversation lives in Memory. Any worker can pick up any thread.

Decision · 03

Zero static credentials between commit and AWS.

GitHub Actions assumes an IAM role via OIDC. No long-lived access keys, no rotation ritual. The trust policy on mia-github-deploy only allows assumption from this repo, on the master branch — anyone else is denied at the STS layer.

The role's permission is intentionally tiny: it can assume the four CDK bootstrap roles. CDK then does the actual work with its own least-privilege chain. Push → test → deploy → smoke. Roughly four minutes, no human in the loop. 

# trust-github-oidc.json — branch-scoped
"sub": "repo:YanivBohbot/Autonomous-Market-Intelligence-Agent:ref:refs/heads/master"

# Role's only inline permission:
"Action": "sts:AssumeRole"
"Resource": "arn:aws:iam::***:role/cdk-hnb659fds-*-us-east-1"
The fastest secret to manage is the one that doesn't exist. OIDC removed the rotation schedule entirely. Push to master, the deploy is signed by a token that lives six minutes.

Decision · 04

Migrated email from SMTP+passwords to SES + IAM.

The original send_email tool used smtplib against Gmail with an App Password rotated into Secrets Manager. The setup hid two compounding bugs: SMTP_SSL was being called on port 587 (a TLS-upgrade port), and the simulation gate didn't catch the @example.com placeholder sender. Both invisible until the first real send.

Swapped to boto3 SES. No port. No password. The runtime role is scoped to a specific verified sender identity ARN — ses:SendEmail on one identity, nothing else. Boto3 is lazy-imported inside the function so the slim-image dependency stays out of the dev test environment.

The probe returned a SES MessageId. Then the email arrived. Two pieces of evidence — one from AWS, one from a real inbox — closed the loop.

§ 05 — Quality

A smoke test that lied, and a QA pass that didn't.

The original smoke test was four cases, all green. It asserted only that the agent's response status was completed or interrupted. The agent met that bar by gracefully apologising when tools were broken, or by hallucinating plausible numbers from its training data. Real assertions had to ground in real tool output.

Before
Smoke test: 4 / 4 green.
Production: every tool quietly broken.
Lambdas returned tool=None because Gateway puts the tool name in the Lambda client context, not the event body. The LLM met the status check anyway — by inventing a NVDA price.

Every assertion now grounds in a fact pulled from a real backing store — a known customer name from customers.db, a SES MessageId, a verified file round-trip, a recalled memory value.

Status-equal-completed is not a quality gate. If a model can satisfy your assertion by saying "I'm sorry, I can't access that right now," then the assertion is grounded in apology, not in the system. Pull a specific fact out of the underlying data store and assert on it.
