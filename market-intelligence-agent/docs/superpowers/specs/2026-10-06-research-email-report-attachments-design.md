# Research Email Report Attachments — Design

**Status:** Design and written specification approved by the user on 2026-10-06.

## Goal

Simplify the Research workspace by removing its persistent prompt-suggestion row, and let a user manually attach one previously generated client report while reviewing a `send_email` action. The attachment must be a real email attachment, remain optional, and be validated against the email recipient before any message is sent.

## Success Criteria

- Research no longer shows the `Portfolio value`, `Stock price`, or `Concentration risk` suggestions.
- A `send_email` approval card shows an optional report selector whose initial value is `No attachment`.
- The selector lists only generated reports that belong to the current recipient.
- Selecting a report never bypasses HITL: the user must still approve or submit the edited action.
- An approved attachment is delivered as a MIME attachment through Amazon SES.
- A missing, unsafe, or wrong-client report prevents the email from being sent.
- Existing email approval, editing, rejection, recipient validation, and attachment-free sending continue to work.

## Approved Product Decisions

1. Report selection is manual. The newest report is not selected automatically.
2. Users can choose only from reports already generated by the system; uploading a new file from the approval card is out of scope.
3. Only one report may be attached to an email in this version.
4. The catalog is filtered to the email recipient so a user is not invited to choose another client's report.
5. `No attachment` remains a valid choice even when reports exist.
6. The Research suggestion row is removed rather than replaced.

## Research Workspace Change

`frontend/src/desk/DeskView.tsx` will stop registering persistent CopilotKit suggestions. The Research heading, chat, composer, ordinary chat-file upload, thread history, tool displays, activity rail, and interrupts remain unchanged. Tests will assert that no suggestion configuration is registered.

This change affects only the prompt shortcuts above the Research composer. The existing chat attachment button remains available for adding context to a research conversation; it is separate from an outgoing email attachment.

## Email Approval Experience

The existing `ApprovalPanel` remains the owner of approve, edit, and reject decisions. A `send_email` request gains an `Attachment (optional)` section below recipient, subject, and body:

- The selector starts at `No attachment` on every new interrupt unless the tool call already contains a valid `attachment_filename`.
- While the report catalog loads, the selector is disabled and shows a compact loading state.
- Available options show the filename and generated date, newest first.
- An empty catalog shows `No generated reports available` and still permits an attachment-free approval.
- A catalog failure shows a local warning and still permits an attachment-free approval.
- When the recipient is edited, the catalog reloads for the new value after a short debounce. Any selected report that is not present in the refreshed catalog is cleared.
- If the interrupt does not allow an `edit` decision, attachment selection is disabled because adding a filename would alter the proposed tool call.

With no selected report, `Approve` submits the existing `{type: "approve"}` decision. With a selected report, approval submits an `edit` decision containing all original email arguments plus `attachment_filename`. `Send edited` likewise includes the selected filename and any changed recipient, subject, or body. Reject behavior is unchanged.

## Report Catalog API

Add a lightweight endpoint:

```text
GET /workspace/reports?recipient=<client-email>
```

The endpoint performs a case-insensitive client lookup in `customers.db`, derives the canonical report prefix from that client's name, and lists matching regular files under `WORKSPACE_ROOT/reports`. It returns only metadata needed by the selector:

```json
{
  "items": [
    {
      "filename": "margaret-collins-portfolio-brief-2026-10-06.xlsx",
      "generated_at": "2026-10-06T09:30:00+00:00",
      "size_bytes": 24832
    }
  ]
}
```

Results are sorted by modification time, newest first. This endpoint must not fetch live prices, regenerate a report, or invoke an LLM. An unknown recipient returns an empty catalog rather than exposing files belonging to other clients.

Shared report-catalog logic will live in a focused backend module used by both the API route and the email tool. It owns client-name lookup, canonical report-prefix generation, safe listing, and recipient-aware file resolution. This prevents the selector and sender from implementing different ownership rules.

## Email Tool Contract and Delivery

Extend `send_email` with one optional argument:

```text
attachment_filename: str | null
```

Before sending, the tool resolves the filename through the shared report catalog using both `recipient` and `attachment_filename`. Resolution rejects:

- absolute paths, path separators, and traversal segments;
- files outside the resolved `WORKSPACE_ROOT/reports` directory, including symlink escapes;
- nonexistent or non-regular files;
- filenames that do not match the resolved client's canonical report prefix.

The existing client-recipient middleware remains in place. Recipient-aware attachment validation also happens inside the email tool so the rule still holds if the tool is invoked outside the multi-agent email specialist.

Emails without an attachment keep the current Amazon SES `send_email` path. Emails with an attachment use a standards-compliant `EmailMessage` and SES `send_raw_email`, with a plain-text body and MIME type inferred from the filename. The serialized raw message must not exceed the project's 10,000,000-byte limit; an oversized message returns a clear error before SES is called. Simulation mode performs the same file and ownership validation, skips AWS, and names the simulated attachment in its result.

The email specialist prompt, single-agent tool description, and `docs/TOOLS.md` will document the optional attachment argument. The model is not responsible for choosing a report: the approval card is the intended manual selection surface.

## Data and Security Boundaries

- The frontend receives report metadata, never server filesystem paths.
- The browser submits only the basename selected from the catalog.
- The backend is authoritative for client ownership and path safety.
- A stale catalog is harmless: the tool resolves the file again immediately before delivery.
- A recipient change invalidates the prior catalog and selection.
- No report content is embedded in the HITL interrupt payload.
- No email is sent when attachment validation fails.

## Error Behavior

- Catalog loading and errors stay local to the attachment section; the approval card remains usable.
- If a selected report disappears before approval, the resumed tool call fails clearly and sends no email.
- If SES rejects a raw message, the tool returns the same style of actionable SES error used by the existing plain-text path.
- Rejecting or cancelling an interrupt never reads the selected report or calls SES.

## Testing

Frontend Vitest and Testing Library coverage will include:

- absence of Research suggestions;
- catalog loading, success, empty, and failure states;
- manual selection with no automatic default;
- recipient edits refreshing the catalog and clearing stale selections;
- approve without an attachment preserving an `approve` decision;
- approve or edit with an attachment producing the expected edited tool call;
- disabled attachment selection when `edit` is not allowed;
- reject behavior remaining unchanged.

Backend pytest coverage will include:

- recipient-filtered catalog results and newest-first ordering;
- unknown recipients and empty report directories;
- path traversal, absolute path, symlink escape, missing file, and cross-client rejection;
- attachment-free SES delivery remaining unchanged;
- raw MIME delivery containing the correct filename, content type, body, and recipient;
- simulation mode with and without an attachment;
- no SES call after validation failure;
- multi-agent HITL preserving attachment arguments through approve, edit, and reject flows.

Handoff requires the focused suites, the complete backend and frontend suites, a production frontend build, manual Research/HITL verification, and a restarted local backend and frontend for user testing.

## Documentation and Compatibility

`docs/TOOLS.md` must be updated in the same change as the `send_email` schema. Existing callers that provide only `recipient`, `subject`, and `body` remain valid because `attachment_filename` is optional. No database migration or new frontend dependency is required.

## Out of Scope

- Uploading arbitrary local files from the HITL card.
- Multiple attachments.
- Automatically selecting the newest report.
- Generating a report from inside the email approval card.
- Attaching reports that belong to a different recipient.
- HTML email composition or rich-text editing.
- Changing the Reports page's generation workflow.
