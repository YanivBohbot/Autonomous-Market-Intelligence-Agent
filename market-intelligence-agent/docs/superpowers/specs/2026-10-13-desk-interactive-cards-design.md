# Market Desk interactive cards — design

Date: 2026-10-13. Status: approved in conversation and awaiting spec review.

## Goal

Make the Research and Client chat (Market Desk, CopilotKit v2 over AG-UI) show more of the agent's work as rich, interactive cards. The audience is a recruiter demo, so every feature must work reliably live. As everywhere in this project, numbers are computed in Python, never by the LLM.

Two phases, one implementation plan:

- **Phase A**: three new deterministic tools with their cards (company comparison, what-if simulation, watchlist alerts), a table card for `read_query` results, and static starter suggestions.
- **Phase B**: AG-UI plumbing (`state["ag-ui"]`), `useAgentContext` on the two chat pages, a generic interactive choice card (`ask_user_choice`), and follow-up suggestions after each answer.

Out of scope:
- CopilotKit frontend tools (`useFrontendTool` / `useHumanInTheLoop`). See "Rejected" below.
- Dynamic suggestions generated by the CopilotKit runtime, which needs the Node runtime we don't run.
- Voice support for any new card.

## Existing pattern reused (Phase A)

Deterministic tool → `DISPLAY_NORMALIZERS[tool_name]` in `app/agent/display.py` → `{"summary", "displays": [...]}` envelope via `market_desk_display` middleware → `DisplayPayload` union in `frontend/src/desk/displays/types.ts` → card component → registered in `useToolDisplay.tsx` (`DISPLAYABLE_TOOLS` + `Rendered` switch). Data access goes through the existing wrappers: `crm_tool`, `yf_quote_tool`, `yf_history_tool`, `parse_tool_payload` and `price_from_quote`. The tools therefore work over stdio locally and over the AgentCore Gateway in prod.

Each tool follows `client_portfolio.py`. A pure async core takes injected `run_sql` / `get_price` / `get_history` callables, so it can be unit-tested without the network. The `@tool` wrapper wires in the real MCP tools.

## Phase A

### A1. `compare_companies` (finance_agent)

- File: `app/agent/tools/compare_companies.py`.
- Args:
  - `symbols: list[str]`, 2–4 items, upper-cased and de-duplicated;
  - `period: Literal["1mo","3mo","6mo","1y"] = "6mo"`.
- For each symbol, in parallel (`asyncio.gather`), it fetches the ticker info and the price history over `period`. Per symbol it returns:
  - `name`, `sector`, `price`, `currency`, `market_cap`, `trailing_pe`, `forward_pe`;
  - `range_position_pct`: where the price sits in its 52-week range, 0 = low and 100 = high;
  - `period_return_pct`: last close vs first close;
  - `points`: a list of `{date, value}` rebased to 100 at the first close.
- Symbols whose info or history fails go into `missing: [..]`. If fewer than 2 symbols are valid, the tool returns `{"error": ...}`.
- Display: `{"type": "company_comparison", "period", "companies": [...], "missing": [...]}`.
- Card `CompanyComparisonCard.tsx`:
  - a metrics table with one column per company;
  - a multi-line chart of the rebased series, using the chart library `PriceChart` already uses.

### A2. `simulate_portfolio_change` (portfolio_agent)

- File: `app/agent/tools/what_if.py`.
- Args:
  - `client_name: str`;
  - `trades: list[Trade]`, 1–10 trades. Each trade is `{ticker, action: "buy"|"sell", pct: float | None, shares: float | None}` with exactly one of `pct` / `shares`. `pct` is in (0, 100] and only valid for `sell`; it is a percentage of the current position.
- Core:
  - `load_client_portfolio` gives the "before" state, with live prices.
  - Trades are applied in order, at the live price.
  - A sale larger than the position, or a sale of a ticker the client does not hold, returns `{"error": ...}` naming the trade. Nothing is partially applied.
  - A buy of a new ticker takes its price from `get_price` and its sector from the `companies` table (`None` if the ticker is not there).
  - A position sold to 0 is removed.
  - The "after" state goes through `compute_portfolio_metrics`.
  - Concentration uses the same rule as `compute_concentration_screen`: 30 %, ETF excluded. It is computed before and after.
- Output:
  - `client_name`;
  - `before` and `after`, each with `{totals, positions[{ticker, weight_pct, market_value}]}`;
  - `cash_delta`: sale proceeds minus purchase cost, positive means cash raised;
  - `breaches_before` and `breaches_after`, as ticker lists;
  - `trades`, normalized to shares.
- The tool never writes to the database. Its docstring and the prompt say "simulation only".
- Display: `{"type": "what_if", ...}`. Card `WhatIfCard.tsx`:
  - paired before/after weight bars per ticker;
  - total value before → after;
  - a cash-raised or cash-needed line;
  - concentration badges that show "resolved" (breach before, gone after) and "new" (absent before, breach after).

### A3. `watchlist_alerts` (portfolio_agent)

- File: `app/agent/tools/watchlist_alerts.py`.
- Args:
  - `client_names: list[str] | None = None`, where `None` means every client;
  - `near_pct: float = 5.0`.
- SQL: `watchlists` joined with `clients` (name) and `companies` (name), optionally filtered by client name with `LIKE`, the same way `build_holdings_query` filters. Live price per distinct ticker, in parallel.
- Status per row:
  - `direction=above`: `triggered` if price ≥ alert_price; else `near` if (alert_price − price) / alert_price × 100 ≤ near_pct; else `watching`.
  - `direction=below` mirrors that.
  - `distance_pct` is the signed % from the price to the alert.
- Sort order: triggered, then near, then watching; within a status, by absolute distance, then client.
- Tickers whose price fails go into `unpriced: [..]` and are left out of the rows.
- Display: `{"type": "watchlist_alerts", "near_pct", "rows": [...], "unpriced": [...]}`.
- Card `WatchlistAlertsCard.tsx`: one row per alert with a status badge (red / amber / grey), client, ticker, live price, alert price and direction, and distance.

### A4. `read_query` table

- `DISPLAY_NORMALIZERS["read_query"]` parses the rows.
- The display is suppressed (returns `[]`) when there is only 1 row and 1 column. That is a lookup such as an email address, not a result set. It is also suppressed when the result is an error or empty.
- Otherwise: `{"type": "sql_table", "columns": [...], "rows": [[...]], "truncated": bool}`, capped at 50 rows.
- The card is wired only where `market_desk_display` is wired: portfolio, finance, rag and browser. `email_agent` lookups therefore never render a table.
- Card `SqlResultTable.tsx`: a scrollable table, numbers right-aligned, and a "first 50 rows" note when the result is truncated.

### A5. Routing and prompts

- `SUPERVISOR_ROUTING_PROMPT`:
  - comparing 2+ companies or tickers → `finance_agent`;
  - what-if / "what if" / "simulate" / "et si" on a client portfolio → `portfolio_agent`;
  - watchlist / price alerts → `portfolio_agent`.
- Specialist prompts:
  - Use the new tools for these questions.
  - Never restate numbers the card shows. Reply in one short sentence, as the finance prompt already says for its cards.
  - A what-if is a simulation, never an executed trade.

### A6. Starter suggestions

In `DeskView`, call `useConfigureSuggestions({ suggestions, available: "before-first-message" })`:

- `/research`:
  - "Compare NVDA vs AMD"
  - "Which clients have triggered watchlist alerts?"
  - "What if Margaret Collins sold half her NVDA?"
  - "Which clients hold Tesla?"
- `/clients/:id` uses client-scoped variants:
  - "Summarize this portfolio"
  - "Any watchlist alerts for this client?"
  - "What if they sold half their largest position?"

## Phase B

### B1. AG-UI plumbing

- **State.** `ag-ui-langgraph` merges `{"ag-ui": {"tools", "context"}, "copilotkit": {...}}` into the run input. LangGraph drops keys the state schema doesn't declare. So:
  - add `ag_ui: dict | None` to `SupervisorState` and `ClientContextState`, under the key `"ag-ui"`. A TypedDict with a hyphenated key needs the functional `TypedDict("...", {...})` form or an `Annotated` alias; the implementation picks whichever LangGraph accepts and pins it with a test;
  - check that the specialist subgraphs receive it.
- **Middleware.** `ui_context_prompt`, a `@dynamic_prompt` in `app/agent/middleware.py`. It appends the entries of `state["ag-ui"]["context"]` (`{description, value}` pairs) to the system prompt under "What the user is looking at in the app:". It does nothing when there is no context. It is wired on the router agent and on portfolio, finance and rag.
- **Transports.** `/stream`, `/approve`, voice and AgentCore never set `ag-ui`. Their behavior is unchanged.

### B2. `useAgentContext`

- `/clients/:id` (`ClientWorkspace`):
  - shares the summary shown on screen: client name, total value, P&L, priced positions;
  - shares the selected position. Holding rows become clickable, and selecting one highlights it. The selection is cleared on a second click.
- `/research` (`DeskView`):
  - shares the most recent rich card shown in the chat as `{type, key fields}`. For a comparison that is the symbols; for a what-if, the client and trades; for alerts, the clients.
  - Follow-ups like "add AMD" or "now with 25 % instead" then have a referent.
  - It is derived from the last tool-call display in the message list.

### B3. Interactive choice card: `ask_user_choice`

- **Mechanism.** A backend tool calls LangGraph `interrupt()` with the payload:
  `{"type": "user_choice", "question", "options": [{"id", "label"}], "multi": bool, "allow_other": bool}`.
  It returns the resumed value: `{"selected": [ids], "other": str | None}`. The run pauses and resumes in place through the checkpointer, exactly like HITL approvals.
- **Rejected alternative.** CopilotKit frontend tools (`useHumanInTheLoop`) were rejected. The browser's answer would come back as a new run that re-enters `load_client_context → record_question → supervisor`, and the router would have to recognize it as a tool answer rather than a new question.
- **Who gets the tool.** portfolio, finance and email.
- **Gating.** A `wrap_model_call` middleware removes `ask_user_choice` from the model's tool list unless `state["ag-ui"]` is present. `/stream`, voice and AgentCore therefore never see it, and their interrupt handling stays HITL-only.
- **Prompts.** Use the tool when:
  - a client name matches several clients. `load_client_portfolio` already returns that error, so the agent asks with the matched names as options;
  - a what-if sale has no size. Options: 25 %, 50 %, 100 %, and Other;
  - the user asks to email "the clients with alerts" or a similar group. Multi-select over the matching clients, then the normal `send_email` HITL.
- **Frontend.** `useDeskInterrupt` branches on `interrupt.value.type === "user_choice"`:
  - it renders `ChoiceCard.tsx`: buttons for single choice, checkboxes plus Confirm for multi, an optional "Other" text field;
  - it resolves with `{selected, other}`;
  - every other interrupt keeps rendering `ApprovalPanel`.
- **The approval rail's pending state** still works, because the same `PendingInterruptMarker` wraps both cards.

### B4. Follow-up suggestions after each answer

- **New node `suggest_followups`** between `finalize_turn` and `END`:
  - it runs only when `state["ag-ui"]` is present and the turn ended with an AI answer, not an interrupt;
  - one cheap call (the specialist model, temperature 0, `with_structured_output(list of 3 {title, message})`) gets the last question and answer;
  - the model call carries `{"emit-messages": False, "emit-tool-calls": False}`, like the router, so nothing streams into the chat;
  - it writes `state["suggestions"]`;
  - on any error it writes `[]` and never fails the turn.
- **Frontend.** `DeskView` reads `agent.state.suggestions`, from the AG-UI state snapshot after `RUN_FINISHED`. It passes them to `useConfigureSuggestions({ suggestions, available: "after-first-message" })`, replacing the starters.
- **Risk to verify first.** Does `ag-ui-langgraph` emit `suggestions` in its state snapshot? If it does not, the fallback is to add `suggestions` to the `/copilot/market-desk/history` response and read it there after `run_finished`. That path already exists and is already reloaded.

## Testing

- **Backend unit tests** (pytest, no network, using the injected callables):
  - comparison: rebasing, 52-week position, missing symbols, fewer than 2 valid;
  - what-if: pct and shares sells, buys of a held ticker and of a new ticker, oversell or unheld → error with nothing applied, a position closed to 0, breach resolved or new, `cash_delta` sign;
  - alerts: above/below × triggered/near/watching, sort order, unpriced tickers, client filter;
  - each normalizer, including the `read_query` 1×1 suppression and the 50-row cap;
  - `ui_context_prompt` with and without context;
  - the `ask_user_choice` gating middleware;
  - the interrupt payload and resume shape;
  - `suggest_followups`: runs only with AG-UI, writes `[]` on error;
  - routing-prompt assertions for the three new intents.
- **Frontend** (Vitest): one test per new card, plus the `useDeskInterrupt` branch (choice vs approval) and the suggestions wiring.
- **Docs**: rows and per-tool sections in `docs/TOOLS.md` for `compare_companies`, `simulate_portfolio_change`, `watchlist_alerts` and `ask_user_choice`; add the read-only ones to `READ_ONLY_TOOLS`; update the CLAUDE.md tool table.
- **Live QA, once at the end** (real browser, `qa_*` threads):
  - click the 4 Research starters;
  - one ambiguous-client choice;
  - one what-if with no size;
  - one click on a follow-up suggestion;
  - on `/clients/:id`, select a position and ask "explain this position".

## Risks

- **Hyphenated `ag-ui` key in a TypedDict state.** Verified in B1 before anything else in Phase B.
- **`suggestions` in the AG-UI state snapshot.** The fallback is described in B4.
- **Router misrouting.** Covered by prompt tests plus the live QA. The same probe method as the 2026-10-13 routing fix: `router_agent` directly, several phrasings.
